# Swarma Router own-domain interface contract

Contract: `swarma-router/0.1.0`. Draft revision: 4. Date: 2026-10-31.
Status: proposed documentation for review, not a released protocol or a qualified external adapter.

## Scope and evidence

This draft specifies the router's own domain boundary, grounded in accepted concept R3, SHA-256 `5d8ddf621eb841c87f7375ced96f6097ed7a84b2b73ad80ffb15e4ee3e567f9b`. The domain operations and ports below are proposals owned by this module. They are not assertions that a board, product-card service, host, broker or Curator exposes these method names, schemas or guarantees. An adapter must translate a counterpart's separately confirmed contract; an unsupported guarantee is unavailable, never emulated as admitted behavior.

No implementation, plugin, weights, installation, live lifecycle action, credentials or skill adoption is delivered here. The module remains independent. Future skill examples must name the released contract version and pass its conformance cases. No shared-specification change is implied by accepting this own-domain proposal.

## Representation and validation

The proposed first presentation is bounded UTF-8 JSON objects. Domain inbound/outbound budgets below apply to public operations; internal port envelopes are separately limited to 262144 bytes and a complete OperationRecord to 196608 bytes, measured before reservation/update. Each request/response explicitly carries `contract: "swarma-router/0.1.0"`. This draft accepts only objects, arrays, strings, booleans, null and signed integers in the exact range -9007199254740991 through 9007199254740991; no floating-point/exponent numbers, duplicate object keys, invalid UTF-8 or unpaired surrogate escapes. Inbound operation envelopes are limited to 65536 encoded bytes; outbound envelopes to 131072 bytes. Canonical encoded SelectionInput is limited to 49152 bytes and Decision to 24576 bytes. Before DecisionStore.Put, construct and measure the complete Explain envelope with a maximum-length request_id: it must fit 98304 bytes, leaving transport-envelope headroom. A record that fails this aggregate admission is not stored or actionable; Recommend returns a bounded error with invalid_request and subject=output_budget, rather than a misleading replayable decision. Recommend output is likewise measured before return. Receipt envelopes are limited to 32768 bytes, pre-effect error envelopes to 4096 bytes. Every Reason array has at most 16 entries and every evidence array at most 16 RevisionRefs; full external evidence is referenced, not embedded. All other arrays together must fit their containing aggregate byte budget. A 4096-byte recovery response budget independent of verbose evidence retains the reserved operation ID and last known durable revision; store capacity for bounded receipt updates is admitted before effects. If later evidence exceeds a response budget, retain it in the owner store and return a bounded RecoveryReceipt referencing the already reserved operation when persistence is unavailable, or persist a bounded truthful unknown Receipt with safe evidence references when the store works; never erase state, drop correlation or invent a clean failure. Error/receipt reasons are chosen from a deterministic bounded summary specified before execution, not silently truncated input/evidence. Every successful stored record must round-trip through bounded Explain; syntax-valid but over-budget derived records fail admission before actionability. These budgets are proposed protocol choices, not measured limits. Oversized text or collections are rejected, never silently truncated.

All fields listed for a record are required; `T|null` permits explicit null. A tagged union includes exactly its tag and listed variant fields. Unknown fields/variants return `invalid_request`; incompatible versions return `unsupported_version`, all before effects. Optional plugins are configured explicitly, not discovered through implicit paths. An absent configured plugin is not an empty successful source result.

## Authority, snapshots and time

An effectful call runs with a trusted `ExecutionContext` supplied by the embedding host: `{caller: Ref, project: Ref, caller_chain: RevisionRef, attenuation: RevisionRef, authority_verdict: RevisionRef, now: Time}`. Transport verification and production of this context are adapter/caller responsibilities awaiting qualification. Arbitrary JSON fields cannot mint a caller or a permission verdict. A missing, expired or unknown authority verdict permits no action. The requesting caller's verified attenuated chain must reach the Launcher/dispatcher execution boundary. Effective target privileges are bounded by the intersection of that chain, current owner policy and the pinned profile; a target profile cannot broaden caller rights. A missing or insufficient chain refuses before launch, even for a highly suitable model. This is required adapter semantics, not a claim that a dispatcher API is already available.

Recommendation consumes a caller-supplied frozen `decision_time`; the pure selector reads no files, network, live clock or inference engine. Effect execution obtains fresh trusted time and fresh authoritative projections through its ports. A historical decision time is never used as an action-time clock. Expiry is exclusive: at `now >= fresh_until` a projection is stale.

All present/absent sources require observed_at < fresh_until, observed_at <= evaluated time < fresh_until. `SourceResult<T>` is the following closed union, with T fixed by interface:

- `present`: `{status, revision: RevisionRef, observed_at: Time, fresh_until: Time, value: <typed projection>}`.
- `absent`: `{status, observed_at: Time, fresh_until: Time, reason: Reason}`. An authoritative completed lookup established the object absent in the named scope.
- `unknown`: `{status, observed_at: Time, reason: Reason}`. A read failed, history is incomplete, authority is insufficient, or state cannot be determined.
- `unconfigured`: `{status, reason: Reason}`. No adapter for this source is selected.
- `invalid`: `{status, reason: Reason}`. The adapter supplied an incompatible or malformed result.

The implicit field `status` above is the exact literal naming that variant. For a live call the port request names project, subject and expected revision or explicit null; a reply for a different scope/subject is invalid. Read failure cannot become `absent`. Fresh absence may refuse an unknown member; it does not authorize creating one. Freshness windows and trust provenance must be justified by the counterpart contract rather than invented by an adapter.

The frozen `Snapshot` has exactly `{task, card, worker, catalog, policy, usage, vendor_limits, local_resources, schedule, preferences, estimator}`, each a SourceResult with the projection below. Arrays of keys representing sets must be unique; duplicate member/catalog-configuration/event identities are rejected. Qualification records use the full semantic QualificationKey defined below, so distinct origin/task/role/difficulty keys may legitimately share a destination configuration.

It is an explicitly supplied, source-attributed resolved evidence/policy assessment for the exact task/configuration/role/difficulty and Origin/destination worker revision, not a classifier-generated permission. Evidence must support any true verdict and cost bounds must share the comparison basis with lower <= upper. These are total remaining accepted-work cost bounds including transfer/rework/time/uncertainty; transition_cost is an explanatory component already included, not added a second time. Transition assessments cannot be reused across origins, tasks, handover revisions or destinations. Missing/mismatched/expired assessment is insufficient evidence; false hard verdict excludes the option. Admission still requires separate exact admitted membership and fresh action-time policy verification. This version consumes these assessments; it does not invent universal quality floors, cost conversions or a trained cost model. Their production and provenance require source-owner qualification. Explicit sufficient labels can support selection with no estimator; absent learned output cannot guess easy work. Incomplete text forbids an automatic difficulty downgrade.

For reviewer work, producer independence and required fresh context are hard filters before cost, preference, hysteresis or reuse. A producer or context exposed to the candidate cannot become an independent reviewer by choosing a different model label. The actual host owner's runtime/model/reviewer-class restrictions must also pass before ranking; unknown provenance or an unresolved owner restriction cannot count as passed. A null general independence-rule reference is not evidence that review independence is unnecessary. These checks do not copy one operator's current model list into a universal policy.

## Deterministic temporal admission and joint event plans

Timing is not cost. `TimingAssessment` is `{origin: Origin, configuration: Configuration, task: RevisionRef, schedule: RevisionRef, start_kind: stopped|replacement|running_delivery|continuation, assessed_at: Time, not_before: Time, queue_upper_ms: integer, pre_launch_upper_ms: integer, launch_upper_ms: integer, post_launch_upper_ms: integer, dispatch_upper_ms: integer, execution_upper_ms: integer, valid_until: Time, evidence: RevisionRef[]}`. Nonnegative safe-integer millisecond durations have distinct scopes: queue begins at admission_at and precedes pre-launch preparation; pre_launch covers gate/quiesce/handover/stop through positive absence; launch covers the physical launch through liveness; post_launch covers restoration/input reconciliation/readiness; dispatch covers final broker delivery or input-resume acknowledgement before logical execution; execution covers remaining accepted-work completion. They are disjoint, not an aggregate transition cost added again. Unsupported bounds cannot become zero. Checked sums/calendar arithmetic must remain representable; otherwise invalid/insufficient evidence, never clamp. For running_delivery, pre_launch/launch/post_launch are supported zero; for continuation all except execution are zero and no new launch/delivery/resume event is requested. stopped/replacement must use the actual branch's supported preparation/restoration bounds, even when some are genuinely zero.

The assessment must exactly match Qualification's unique key and current source/task/configuration/origin, assessed_at<=decision_time<valid_until. Schedule.resolved_for=decision_time and every relied-upon observed_at<=decision_time<fresh_until. Named-zone recurrence/DST remains adapter-owned with no guessed fold/gap. Hard finish D is min(non-null Task.deadline, Schedule.deadline); both null means no deadline gate. This version provides no lateness waiver; a lateness_policy ref cannot override D.

Allowed intervals and not_before constrain BOTH physical launch (when one occurs) and logical execution start (initial task dispatch/ack or Apply resume), each half-open at the same allowed set. Logical execution start is the actual accepted task-input/dispatch or input-resume gate event; a later acknowledgement does not move that event into a different window. Desired intervals are soft preferences evaluated at logical execution start only. Pre-launch preparation is not a launch or logical start and may precede an interval only under its already authorized task/claim/hold policy; no window rule here grants preparation authority. A joint plan must prove the required future launch AND execution/resume boundaries and finish are feasible before any predecessor gate/stop. Checking just execution time or a final launch fence is insufficient.

`TimingPlan` is `{start_kind: stopped|replacement|running_delivery, evaluated_at: Time, admission_at: Time, prepare_at: Time, launch_at: Time|null, ready_at: Time, execution_at: Time, finish_at: Time, launch_window: Interval|null, execution_window: Interval|null, valid_until: Time}`. It is a conservative supported upper-duration plan, not a claim of observed events or a reservation. Stopped/replacement require non-null launch_at and a window unless explicitly unrestricted; running_delivery requires both launch_at and launch_window null. TimingAssessment.start_kind is inferred exactly from the frozen branch: an already assigned current configuration retained without input is continuation; new delivery to a known running configuration is running_delivery; a positively stopped destination is stopped; same-member configuration replacement is replacement. Mismatched assessment kind is insufficient evidence. Continuation produces no new-start TimingPlan or effect admission; it uses only the separate remaining-work deadline/passive-retention rules. All projected boundaries/finish must satisfy the following deterministic construction, and source/admission expiry must cover the relied-on action boundaries or require fresh revalidation before the next step. A source's validity cannot be extended by the plan.

For stopped/replacement let A=queue_upper_ms+pre_launch_upper_ms, B=launch_upper_ms+post_launch_upper_ms+dispatch_upper_ms and E=execution_upper_ms. Enumerate launch interval L and execution interval X in the sorted allowed set; they may be different intervals. For each pair, compute the earliest admission time T=max(decision_time, not_before-A, L.start-A, not_before-(A+B), X.start-(A+B)). Then prepare=T+queue_upper_ms, launch=T+A, ready=launch+launch_upper_ms+post_launch_upper_ms, execution=T+A+B, finish=execution+E. Require not_before<=launch<L.end with launch>=L.start, not_before<=execution<X.end with execution>=X.start, and finish<=D if present. An unrestricted schedule removes interval bounds and has allowed=[]; use the same equations without L/X start terms, with null launch_window/execution_window permitted ONLY for unrestricted=true. No bounded time infinity is serialized. Thus TimingPlan.execution_window is Interval|null, with null meaning this explicit unrestricted case. For stopped/replacement under unrestricted, launch_window=null too while launch_at remains non-null. Otherwise null cannot bypass a fence.

For running_delivery let H=queue_upper_ms+dispatch_upper_ms and E=execution_upper_ms. For each execution interval X compute T=max(decision_time, not_before-H, X.start-H), prepare=ready=T+queue_upper_ms, execution=T+H, finish=execution+E. Require execution in X and >=not_before, finish<=D. There is no new physical launch. Use the analogous unrestricted construction without X.start. No implicit launch bound may be charged twice or ignored on a stopped/replacement branch. This version plans contiguous supported upper-duration stages; it does not add arbitrary inter-stage waiting to bridge separated windows. Deferral shifts admission before preparation instead. Failure to find such a plan means no supported bounded plan under these inputs, not a platform-wide impossibility claim; extra idle/scheduler semantics would need an explicit versioned assessment, never guessed duration padding.

Reject a pair violating any boundary/deadline. Among feasible plans choose ascending admission_at, then execution_at, then descending desired priority at execution_at, then canonical launch-window/execution-window bytes (null unrestricted has its canonical null order). Desired priority=max(0, priorities of desired intervals containing execution_at); missing desired window never forces delay or exclusion. The candidate is feasible-now only if admission_at=decision_time. A supported later admission time yields defer/next_check at that exact T, no selected candidate or effect. It arms no timer, starts no preparation and consumes no occurrence. Unknown future required observations are not reserved/guaranteed; reevaluate then. If no jointly feasible pair exists return the actual outside_window/deadline_unsatisfied exclusion; required unknown bounds/source/clock produce schedule_unresolved/evidence_insufficient, not a promised plan.

For every feasible stopped/replacement plan, temporal initial-admission valid_until is the minimum of (L.end-A, X.end-(A+B), D-(A+B+E)+1ms), omitting absent/unrestricted cutoffs. For running_delivery it is min(X.end-H, D-(H+E)+1ms). These cutoffs bound the latest initial admission, not the later launch/resume event itself. For example, a valid09:59:20 admission with a09:59:30 cutoff may still resume at10:00:20 if current authority/claims/holds/sources and the remaining30s finish bound pass D10:01; it must not falsely fail merely because initial-admission time is past. Conversely the earlier admission is no waiver for a newly impossible late resume. The +1ms only expresses the inclusive finish<=D rule in this millisecond/exclusive-expiry contract; start at interval.end remains forbidden. Take the exact minimum with every relied-on timing/source/qualification expiry and decision_time+maximum_decision_age_ms; an implementation may not invent another earlier/later value for the same frozen inputs. Unsafe arithmetic or valid_until<=decision_time yields no actionable plan. For defer, advice is informational and not Apply-authorizing; valid_until still cannot outlive its relied-on evidence. Recommendation ranks feasible-now candidates by existing cost/desired/preference rules; when none exist but supported later plans do, return the earliest T with the canonical configuration tie-break. A required unknown candidate cannot be fabricated into a later plan.

Concrete joint witness: at09:59:20, A=0, B=60s (launch only), E=30s, allowed[10:00,10:02), D10:01. Earliest permitted admission/launch is10:00, execution10:01, finish10:01:30>D: no feasible pair, no gate/stop. It is forbidden to call09:59:20 launch feasible merely because its execution10:00:20 and finish10:00:50 fit. With interval start09:59 and all other facts unchanged, T09:59:20/launch09:59:20/execution10:00:20/finish10:00:50 passes. With original interval but D10:02, the10:00/10:01/10:01:30 plan genuinely supports defer to10:00 and becomes feasible-now on reevaluation. Exact-end launch OR execution is rejected; finish exactly D is allowed.

A current continuation is not a new start: a start-window ending does not stop it. Its assessment has start_kind=continuation, supported remaining execution bound and no launch/dispatch preparation. A hard deadline may be claimed feasible only when decision_time+execution_upper_ms<=D. Passive keep of a held/dependency-blocked session is only configuration retention and makes no claim to complete by D or permission to resume. Missing hard feasibility evidence cannot authorize new work or destructive change. Current-ineligible and explicit target constraints remain as specified in the frozen eligibility section.

Route obtains a fresh TimingAssessment and computed TimingPlan for its actual running-delivery/stopped branch even without Recommend; Apply obtains the replacement plan and revalidates it before claims/gate/stop and every effect boundary. Admission/EffectBinding carry this complete initial plan. Later phase checks use the proved completed stages and supported bounds for the remaining stages of the same operation/target, persist their updated owner admission/binding before effects, and do not rerank or mint a new Apply from an expired decision. Snapshot resolved_for remains its original evaluation binding; current UTC window predicates are evaluated with the fresh phase clock, not by pretending that clock equals the historical decision_time. Source drift/holds/authority loss still refuse the affected next effect and preserve actual partial state. Effect owners enforce actual launch and logical execution/resume with explicit not_before/not_after bounds from its exact windows/remaining finish bound, and freshly validate time/observations/policy/holds after real queue/gating/stopping/restoration delays. Faster steps may require preserving the admitted closed gate until a planned lower boundary or recomputing an equally authorized jointly feasible plan; they never authorize an early launch or input resume. The operation owner may honor these bounded fences only where its admitted action contract supports them; this pure proposal registers no unattended scheduler. A plan that was impossible initially refuses before damage; a previously feasible plan made infeasible by actual delay preserves truthful partial state, saved handover and gate, with no illegal launch/resume/rollback. Lost resume acknowledgement remains unknown gate/state. Unchanged source revisions never excuse a crossed time predicate.


## Pure frozen worker eligibility and assessment resolution

The versioned selector applies this section before costs, desired preferences, hysteresis or estimator ranking. Syntax/source validation and semantic eligibility are separate. For each candidate resolve the exact Task, Card, Member, Worker row, CatalogEntry and matching policy assessment from SelectionInput; no files, live lookup or unspecified adapter verdict participates. Same-vendor/model names do not identify a member. Source absence is a known exclusion where authoritative, while missing/stale/unknown/mismatched source or required field is insufficient evidence for that candidate. A usable B remains selectable when only A has unknown state. If the shared task/card/policy source itself is unknown/invalid, no candidate obtains that missing shared clearance.

For assign/switch advice and any new task delivery, require all of the following frozen checks:

1. SelectionInput.project equals Task.project and Card.project; the exact candidate member occurs once in Card.members, project occurs in Member.project_scope, Task.role occurs in Member.roles and CatalogEntry.compatible_roles. Configuration.member/profile bindings, exact admitted tuple, pin and effort compatibility must pass. A proved mismatch excludes before ranking; no favorable qualification overrides it.
2. Task.dependencies_ready=true. False excludes new starts/assign/switch with dependencies_not_ready. Unknown required task data is evidence_insufficient. An estimate or desired time cannot manufacture dependency readiness.
3. The corresponding Worker row exists and has known liveness/session/configuration as required for its branch. Known running requires its exact session/configuration; stopped requires positive absence. Unknown liveness is insufficient. Member holds are Worker.held: false is required for active assignment/adaptation/delivery, true excludes with member_held, null is unknown. A held current origin also forbids a new switch/adaptation recommendation until its hold is cleared; cost savings cannot override no-wake state.
4. Worker.active_assignments is an authoritative complete unique Ref set, or explicit null when unknown; Member.concurrency_limit is positive. Let n be its cardinality and t be Task.task. Required occupied slots are n if t already occurs, otherwise n+1. Require occupied<=concurrency_limit; larger excludes with capacity_unavailable. Do not count t twice or presume a stopped worker has zero assignments. Null assignments cannot clear capacity. This is frozen feasibility only; it reserves nothing. The task-owner assignment authority remains separate from this count, and the actual Claim owner must atomically validate current assignment/slot state later.
5. The unique exact Qualification must pass floor, independence, fresh context, actual owner runtime restrictions and billing; its cost/timing/observation evidence must match the exact frozen task/origin/destination/configuration. Required quota/resource/timing gates then run on the actual frozen observations. Cheap or all-true quality booleans cannot erase an earlier project/role/dependency/hold/capacity exclusion.

Passive keep is a separate no-effect advice branch for the exact current configuration/session already carrying t, with Task.assignee=current member, t in known active_assignments and n<=limit. It preserves the present gate, hold and dependency state; it neither routes input, resumes work, consumes another slot nor authorizes work while held or dependencies are unmet. Known held=true or dependencies_ready=false may therefore produce passive keep with member_held/dependencies_not_ready reasons when the exact current configuration still passes project/role/admission/quality/independence/runtime/billing hard rules; it is not an eligible new-start option. Unknown hold/assignment/current identity cannot establish this passive-retention exception. A member at limit1 with [t] is not full for continuing the same t. A member at limit1 with [other] is full for new t. A known forbidden current configuration is current_ineligible; do not use passive keep to evade owner restrictions or invent stop/resume authority. Any actual continuation/input remains subject to current owner holds/dependencies and fresh admission.

The rules constrain assign/switch candidate ranking, current-ineligible reporting and the current side of switch comparison. Excluded candidates carry their exact reason in alternatives and cannot win; uncertain candidates carry evidence_insufficient plus the source reason. If a qualified feasible-now B exists, A's hold/full/unknown state does not force blanket abstention. If no candidate is proven eligible and at least one lacks required evidence, return insufficient_evidence; if all are proven excluded, no_candidate. A permitted passive current can be kept under its exact exception, except that an explicit different target constraint cannot be pretended satisfied. This section never makes a keep decision an Apply token or replaces action-time atomic claims.

`QualificationKey` is `{origin: Origin, destination_worker: RevisionRef, task: RevisionRef, configuration: Configuration, role: Ref, difficulty: trivial|routine|standard|hard|critical}`. Equality compares every field structurally after canonical set normalization; Origin includes its full current session/context/handover/WorkerSet binding or the explicit initial tag. Policy.qualifications MUST contain at most one resolved Qualification per semantic key and exactly one matching assessment for any positive qualification, regardless of cost bounds, evidence, booleans, timing or expiry. These latter fields are the assessment value, not disambiguators. The selector looks up the exact key derived from the frozen input/candidate; it does not select first/last/cheapest/most recent matching evidence.

Two records with the same semantic key, even identical assessment values, make the supplied Policy semantically invalid with source_invalid; Recommend returns insufficient_evidence, selected=null, reason source_invalid subject=qualification_key_conflict plus evidence_insufficient, and no actionable stored switch. This whole-policy invalid-input rule is deliberately explicit; it is distinct from a single, consistent Qualification with a false hard boolean, which proves that candidate excluded. Stale single assessment is insufficient evidence, not a negative verdict. Distinct origins/tasks/configurations/roles/difficulties are separate valid keys, including A-origin and B-origin records sharing a destination. Historical/conflicting alternatives must be resolved by the authoritative evidence source before becoming one frozen Policy; the router cannot choose favorable evidence. This conflict rule is part of selector version swarma-router/0.1.0 and therefore replayed/identity-bound. Source-invalid information may be stored for explanation if budgets/privacy allow, but cannot be acted on.


## Domain operations

Every call returns `{contract, request_id: Ref|null, result}`. Null is permitted only for a pre-effect invalid_request when the incoming request_id is missing or invalid; a valid request_id is echoed exactly and every reserved operation keeps its original correlation. Request and response IDs match. A request names the operation in its envelope `operation`. Non-effectful validation errors use `{kind: "error", reasons: Reason[]}` with at least one reason. Once an effectful operation is reserved, its result is a durable Receipt, including failures, or an explicitly non-committed RecoveryReceipt when durable read/write is unavailable; an ambiguous effect never collapses into a pre-effect error.

### Route

`Route` request fields: `{contract, operation: "route", request_id, project: Ref, task: RevisionRef, member: Ref, card: RevisionRef, expected_session: SessionRef|null, idempotency_key: Ref}`. A null expected_session asks the router to resolve current state; a non-null value is a strict compare condition. Manager liveness inspection is unnecessary. The task and member must belong to the trusted project. A board assignment must either already admit this member or be covered by an explicit task-owner assignment capability validated during admission; Route itself never silently edits board assignment.

Before effects, resolve fresh task/card/member state and acquire the current resolved Policy through policy.read_projection as specified below; check task revision, dependencies, member admission, project/role/hold/concurrency, permissions and source readiness. Resolve required plugin capabilities. If Broker is unconfigured or refuses the operation contract, do not launch even a stopped member. Acquire the execution owner's atomic assignment/slot claim with expected revisions; a local read of spare capacity is insufficient. This draft's Claim port below is a required abstraction, not proof a host implements it.

- Fresh running: bind the admitted existing generation, recheck its claim and delivery generation, then Broker.Deliver. Exactly zero Launcher calls.
- Fresh stopped: require Launcher and positive stopped evidence; preflight exact card profile/runtime/model/effort/placement, launch once under the same operation/claim, prove liveness for the returned generation, then Broker.Deliver. Failed/unknown liveness never permits delivery.
- Unknown liveness, held/unknown hold or unknown assignment coverage, absent/unadmitted member or stale/changed expected revision: refuse before effects. The caller can supply a new request after the missing fact is resolved; no speculative start occurs.

Route never implicitly changes model/effort, runs a classifier to replace the selected member, or applies a recommendation. A newer card/policy/task during the action must be revalidated by the execution owner at the effect boundary. Without that support, a live adapter cannot qualify.

### Recommend and Explain

`SelectionInput` is `{project: Ref, decision_time: Time, snapshot: Snapshot, current_member: Ref|null, target_member: Ref|null}`; these are ALL semantic selection inputs. `Recommend` fields: `{contract, operation: "recommend", request_id, input: SelectionInput, record: store|skip}`. current_member explicitly identifies the current work being compared; null means initial assignment. A named target_member constrains the alternatives, without hiding the current candidate needed for transition comparison; null permits comparing admitted members. Each candidate's member must have a corresponding fresh worker row or be marked unknown/ineligible. Apply the complete frozen eligibility and unique QualificationKey rules above before ranking. No launcher/broker/claim operation is called. The estimator result is supplied/frozen before pure selection. An optional inference adapter may prepare it separately, with its own timeout and artifact identity, never inside replay.

Recommend returns `{kind: "recommendation", decision: Decision, record_status: stored|unavailable|not_requested, reasons: Reason[]}`. record=skip makes no Put and returns not_requested; record=store attempts bounded atomic Put and returns stored or unavailable. This storage choice is explicit and excluded from pure selection identity. Record status is the separate storage outcome, never authority or part of the pure selector's result. Only stored supports later Explain/Apply; unavailable/not_requested makes the advice informational even when its data expiry lies in the future. A digest by itself proves neither storage nor permission.

Decision fields: `{id: Digest, selector_version: Ref, project: Ref, decision_time: Time, valid_until: Time, snapshot_digest: Digest, selection_input_digest: Digest, apply_mode: same_member_replace|unsupported_destination|null, kind: keep|assign|switch|defer|no_candidate|insufficient_evidence|current_ineligible, current: Configuration|null, selected: Configuration|null, expected_session: SessionRef|null, alternatives: Alternative[], reasons: Reason[], next_check: NextCheck}`. Alternative is `{configuration: Configuration, eligible: boolean, cost_lower: Cost|null, cost_upper: Cost|null, transition_cost: Cost|null, reasons: Reason[]}`. NextCheck is `{kind: "event", source: Ref, subject: Ref}` or `{kind: "time", at: Time}` or `{kind: "none"}`; it does not register a subscription or timer.

All selected tuples are exactly admitted/compatible/qualified candidates. `keep` selects current configuration/session unchanged and is passive no-effect advice under the frozen eligibility exception; it never clears a hold/dependency or permits input/resumption; `switch` names a changed configuration or member and carries the current session; apply_mode is same_member_replace or unsupported_destination only for switch and is null for every other kind; `assign` has no current worker; all other kinds have selected=null. `current_ineligible` identifies a forbidden current configuration and eligible alternatives without silently permitting continued execution or choosing an unqualified switch. `defer` includes a supported future time/event; unknown future quota is no promise. valid_until is the earliest relevant source/qualification expiry, decision_time + maximum_decision_age_ms and the joint temporal cutoffs above; a decision already expired is not actionable. If required policy/expiry evidence is unavailable or Policy has a duplicate QualificationKey, only an informational insufficient_evidence decision is produced with selected=null and valid_until=decision_time, preserving source_invalid/evidence_insufficient for a qualification-key conflict. No reservation lifetime is inferred from this informational expiry.

Compare conservative total accepted-work/rework/time/transfer/uncertainty costs on one explicitly resolved basis. Current configuration retention cannot violate hard requirements; passive keep preserves an existing hold/dependency gate and is not execution or resume permission. A switch requires new upper bound plus margin < current lower bound and minimum dwell; unknown bounds yield keep only for still-permitted current work, otherwise insufficient_evidence. All model/vendor switches include context reconstruction cost; effort-only preservation must be supported by the runtime's declared transition contract. No catalog/model name hardcodes strength or authorizes metered spending.

For an initial assignment, rank qualified candidates with known cost bounds by ascending total upper bound, then descending desired-window priority at the assessed start (outside desired windows scores zero), then explicit preference order, then canonical Configuration byte order. For a switch, apply that order only to alternatives that satisfy every transfer/margin/dwell constraint; otherwise keep a still-permitted current worker. No eligible candidate gives no_candidate; eligible candidates lacking required evidence give insufficient_evidence. If target_member differs from current_member and keeping would violate that explicit target constraint, return insufficient_evidence/no_candidate with the conflict, never pretend the target was honored. Missing last-switch evidence cannot prove a positive dwell requirement; an explicit zero dwell needs no historical timestamp. Ties and abstentions use these rules rather than model names or map iteration order.

`Explain` fields: `{contract, operation: "explain", request_id, project: Ref, decision_id: Digest}`. Return `{kind: "decision", decision, input: SelectionInput}` only for an authorized stored project decision. If the scoped record is absent/unavailable, return an error with decision_not_found/store_unavailable; never silently recompute under changed inputs. Storage must retain the frozen data needed to replay during the decision's actionable lifetime. Text/privacy policy may refuse storage; such a recommendation can be informational but must not claim replayability or an actionable Apply token.

### Apply explicit adaptation

`Apply` fields: `{contract, operation: "apply", request_id, project: Ref, decision_id: Digest, expected_task: RevisionRef, expected_card: RevisionRef, expected_session: SessionRef, idempotency_key: Ref}`. This version accepts only a stored unexpired `switch` decision. `keep` means retain the admitted current worker without a lifecycle call; passing it to Apply returns decision_not_actionable with zero effects. `assign`, `defer` and informational/error decisions likewise cannot be interpreted as a switch. Initial assignment goes through an explicit Route request to an admitted card member, not a hidden Apply fallback.

Retrieve the exact stored SelectionInput and verify selection_input_digest, snapshot_digest and Decision.id; expected_task/card/session must equal its task/card revisions and current Origin/session. Revalidate the complete frozen eligibility/unique-assessment predicates and the jointly feasible replacement event plan before any gate/stop, then current task/assignment/card/configuration/catalog/policy/usage/vendor_limits/local_resources/schedule, every relied-on hard assessment and generation with fresh action time, including time predicates even when revisions match. Require a current switch authorization; recommendation is not permission. Apply in 0.1.0 supports only same-member replacement in the same slot, slot owner and placement, with an exact current running predecessor; set apply_mode=same_member_replace only for that case. A cross-member destination, different slot/placement, already-running other destination or unresolved destination is apply_mode=unsupported_destination and Apply returns capability_unavailable with zero claim/gate/stop/launch/delivery effects. No hidden Route or stopping the destination repairs this restriction. Recommendation may explain such a switch but cannot make it executable through this version. Acquire the execution owner's fenced transition claim covering the task assignment, member, slot, predecessor generation and exact successor configuration before any gate/stop effect. Fresh destination/slot state and owner identity must match; another manager's change or unknown state refuses before predecessor damage. There is no unconditional launch of another running member. Route may independently bind a running member only under its own authorized request, not as Apply fallback. Missing Launcher or admitted restore/gate/status semantics gives an unavailable/refused result, leaving current work unchanged. Expected source drift returns stale_decision; it does not silently regenerate a decision.

Admitted execution owner owns the complete sequence: close input for the expected predecessor generation; prove quiescence/no unresolved active effect; persist permitted bounded handover and authorized task revision; stop predecessor and prove absence for the claimed slot; revalidate actual-start timing/admission and positive slot absence under that claim after any delay; launch exact selected configuration once; verify successor generation/binding/liveness; initialize/restore authorized task and permitted handover under reset rules; reconcile held/unknown input outcomes; acknowledge readiness for that successor generation; then resume input for that generation and report success. Any operator hold or admission loss is rechecked by that owner and cannot be erased by replay.

The router observes durable phases and delegates execution through the lifecycle adapter; it never writes terminal input, controls foreign PIDs or creates a second input writer. A host claiming readiness without restoration and reconciliation cannot satisfy the port contract. No specific native-resume command is required. Restoration, held-input reconciliation or readiness-ack failure remains partial/unknown with gate closed and successor identity/handover preserved. Status reconciliation of the same operation/generation may complete it without another launch or blind input replay. Unknown stop forbids successor start; forbidden predecessors are never automatic rollback targets. No automatic replacement vendor, relaxed permissions or native-runtime bypass follows refusal. Genuine model-unavailability handling follows the affected owner's separately verified model-availability rule; neither a low-cost ranking nor this contract grants an automatic downgrade or alternate-profile/provider retry around a fresh host/Curator refusal.

## Durable operation receipts and reconciliation

`Status` request fields: `{contract, operation: "status", request_id, project: Ref, operation_id: Ref}`. It returns the latest authorized durable Receipt or an error `operation_not_found`/`store_unavailable`; failure to read is not proof that the operation did not occur. Responses from another scope/generation cannot be merged by name or PID.

Receipt fields: `{receipt_status: "durable", operation_id: Ref, operation_kind: route|apply, request_digest: Digest, idempotency_scope: Ref, revision: integer, task: RevisionRef, member: Ref, state: pending|succeeded|refused|failed|partial|unknown, phase: Phase, effect: none|present|unknown, predecessor: SessionRef|null, successor: SessionRef|null, delivery: DeliveryRef|null, handover: RevisionRef|null, gate: not_applicable|open|closed|unknown, claim: ClaimBundle|null, reasons: Reason[], updated_at: Time, reconcile_required: boolean}`. DeliveryRef is `{owner: Ref, id: Ref, destination: SessionRef, task: RevisionRef, state: queued|acknowledged|rejected|unknown}`. Effect records operation history: even a confirmed later release does not erase an earlier acquired claim or launch. Refused requires effect=none; after any effect a resolved rejection may be failed only when no retained/uncertain effect remains, otherwise partial/unknown; `failed` requires a known resolved outcome with no unresolved or retained partial effect; any retained partial effect or uncertainty requires partial/unknown rather than a clean refusal. `succeeded` requires reconcile_required=false and the operation-specific completion condition below.

`Phase` is one of `validated`, `claimed`, `gating`, `quiescing`, `handover_saved`, `stopping`, `predecessor_absent`, `launching`, `successor_observed`, `restoring`, `reconciling_input`, `ready`, `resuming`, `delivering`, `delivered`, `complete`, `refused`. An unavailable early operation can return a refused receipt with no claim/effect. Route uses validated/claimed/launching/successor_observed/delivering/delivered/complete; Apply uses the lifecycle phases. Intermediate state pending is legal only while the owner knows the operation is actively progressing; lost execution knowledge becomes unknown. Phase describes the last durable step/attempt; it does not assert success of the next one.

`RecoveryReceipt` is `{receipt_status: "recovery", operation_id: Ref, project: Ref, last_durable_revision: integer|null, state: "unknown", effect: "unknown", reconcile_required: true, reason: Reason}`. It retains the already reserved operation correlation and makes no claim that a new revision or outcome was persisted. No invented revision, erased effect, new idempotency key or retry authority follows it; return to the same OperationStore/owner Status. A known last durable record is retained, not overwritten with a fabricated unknown ledger revision. Before any reservation failure the usual bounded pre-effect error applies. Status with an unreadable store may still return store_unavailable; that read error is never absence. The public operation result distinguishes Receipt/RecoveryReceipt by receipt_status. RecoveryReceipt is bounded to 4096 bytes and never requires embedding a lost ClaimBundle or raw evidence.

The operation ledger reserves scoped idempotency before any effect, including Claim.Acquire, and persists request digest, owner operation ID and the last known phase. A write failure before reservation means no effects may start. A persistence or response failure after a possible effect requires reconciliation; an HTTP error or missing receipt is never absence evidence. Production must delegate durable coordination to an admitted owner or demonstrate an equivalent qualified implementation; an in-memory fixture cannot prove cross-crash safety.

For the same trusted caller/project/operation kind/key:

1. Identical canonical payload returns or reconciles the existing operation. A fresh request_id is correlation only and excluded from the idempotent payload digest.
2. Different task/member/revisions/decision payload returns `idempotency_conflict` before new effects; the existing operation is unchanged.
3. A busy known operation returns its current pending phase, never a second execution.
4. A lost response invokes owner Status by its durable operation ID before any retry. Retrying a transport call is permitted only where that exact owner contract declares it idempotent.
5. Keys, request digests and owner correlation must remain available for the entire actionable/reconciliation lifetime. Terminal audit compaction may keep a permanent non-reusable key tombstone. Lost/expired deduplication evidence never licenses a new effect with that key; return reconciliation_unavailable. A new key is not authority to duplicate an uncertain earlier action.

Ledger revision is monotonic per operation, starting at 1; updates use compare-and-swap against the observed revision. This specifies desired router-ledger behavior; external source revisions remain opaque. Claim validity, operation revision and session generation protect different races and cannot substitute for one another.

Route succeeds when Broker has durably queued or acknowledged the exact task/destination revision and the admission owner confirms the claimed destination generation. It reports that exact delivery state; successful routing is not task execution or completion. Broker refusal after a launched successor is partial with that successor retained, not a clean rollback. If a queued delivery later fails, Status changes the current receipt state to partial (retained worker/claim/effect) or failed (resolved with no retained/uncertain effect), with updated delivery and revision; no silent redelivery occurs.

Apply succeeds only at complete, after expected-generation restoration, held-input reconciliation and readiness are established and input resumption is acknowledged by its execution owner. `ready` with gate closed is not succeeded. If resume is attempted and its acknowledgement is lost, gate becomes unknown and operation state unknown: do not claim it is closed or issue a blind reopen. Supported owner Status must establish whether input actually resumed for the expected generation. If the operation's protection requires a closed gate, request/verify it through the same owner; a lost observation is not a guarantee that physical input stopped. Before resume is attempted, restoration or lost readiness acknowledgement must preserve a verified closed gate. A crash never resets a hold or replays approval/control input.

No cancel operation is defined in 0.1.0. Timeout ends waiting, not the authorized underlying effect. Managers inspect/reconcile Status; stopping an operation or changing its destination requires a separately authorized owner capability and a versioned API, never an undocumented cancellation side effect.

## Proposed adapter ports and capability negotiation

These are router-facing proposed interfaces. Function-like labels describe the adapter contract, not current counterpart commands. Each selected adapter declares `{id: Ref, implementation_revision: RevisionRef, interface: Ref, versions: string[], capabilities: Ref[], counterpart_contract: RevisionRef|null, qualification: RevisionRef|null}`. The caller must independently validate the qualification against its admitted configuration/source-owner record for this exact implementation and counterpart version; a plugin cannot qualify itself by returning a flag or reference. Missing/unverified counterpart contract or qualification permits fixtures/shadow data only and cannot satisfy live effect admission. Interface version must match explicitly; no implicit fallback to a different plugin/runtime. Minimum supported capability checks occur before reserving an effect. The following table summarizes responsibilities; the closed records/action vocabulary below are the exclusive request/result definitions, with no extra method fields implied by these summaries.

| Port | Required own-domain interaction | Absence/refusal/unknown contract |
| --- | --- | --- |
| TaskSource | Read(project, task reference, expected revision) -> SourceResult<Task> | Absent task refuses; stale/unknown cannot satisfy assignment/dependency checks. No board writes implied. |
| MemberSource | ReadCard(project, exact card revision), resolve member -> SourceResult<Card> | Unknown or card-absent member refuses before launch/delivery. No identity provisioning implied. |
| WorkerStateSource | Observe(requested members, expected sessions or null) -> SourceResult<WorkerSet> | Authoritative stopped evidence differs from missing observer/row; unknown is never stopped. PID/command alone is insufficient. |
| ModelCatalog | Read exact supported configurations/profile/effort vocabulary -> SourceResult<Catalog> | Registry absence is unavailable; names alone do not establish compatibility, quality or installation. |
| PolicySource | policy.read_projection -> SourceResult<Policy>, then policy.evaluate -> SourceResult<Admission> with complete snapshot | Must preserve exact admitted tuples, quality floor, spend and review independence. Failure cannot widen permission. |
| VendorObservationSource | vendor.observe -> SourceResult<VendorLimits> | Optional; absent/stale scope remains unknown, not spare quota or overload clearance. |

| TaskEstimator | Estimate bounded authorized text/features with exact artifact/configuration -> SourceResult<Estimator> | Abstention/error remains visible; explicit sufficient labels can bypass inference without claiming a learned result. |
| DecisionStore | Put/Get scoped frozen decision plus complete SelectionInput by digest | Explain/Apply require an authorized actionable record; retrieval error is not absence or a signal to recompute. |
| OperationStore | Reserve(key,digest), CompareAndSwapRecord, GetByKey/GetByOperation | Must durably establish key/owner correlation before effects and preserve reconciliation evidence; unavailable forbids new effects. |
| Claim | Acquire/Validate/Release owner claim for task/member/slot or session transition, with expected revisions and fencing token | Current external owner arbitrates atomically. A claim timeout/status gap is unknown, not expiry proof. No guessed local locking or forced release. |
| Launcher | Preflight, Launch, Stop, Status, Liveness with exact configuration, operation, claim, generation and verified caller attenuation | Reuse one owner operation; target profile never broadens caller rights. Typed refused/unsupported/unknown are distinct. No plain runtime bypass or arbitrary PID kill. |
| Lifecycle | Gate, Quiesce, SaveHandover, Restore, ReconcileInput, Ready, Resume, OperationStatus through the admitted execution owner | Required for Apply; unavailable blocks Apply before stop. Preserve actual phase/gate/session/handover; never synthesize host acknowledgements. |
| Broker | Deliver/DeliveryStatus with exact authorized task, destination generation, operation/key/claim | Durably queued is different from runtime ack; lost response reconciles same delivery. No second input writer or raw terminal injection. |

Launcher and Lifecycle may be implemented by the same adapter, but their capabilities and owner guarantees remain separately declared. Stop and generation fencing belong to the admitted lifecycle/process owner; exposing the proposed method does not create permission to stop a process. A Curator adapter can own command translation only where supported; host-managed restore/gating is not invented as a Curator feature. Profiles remain pinned and validated; unsupported launch/readiness or native restoration returns an explicit capability gap.

A proposed configuration record is `{contract, project: Ref, plugins: [{interface: Ref, adapter: Ref, version: string, configuration_ref: RevisionRef}], policy: RevisionRef}`. Exactly one adapter per required interface is selected; duplicates, unsupported versions and unknown fields fail validation. An optional interface omitted from plugins is unconfigured. Configuration references are opaque module-owned data references, not arbitrary shell/load paths. Static linked implementations are the initial extension model; dynamic library loading is not part of this contract. No real plugin IDs, package coordinates, configuration filename or discovery command are declared released here.

### Closed router-facing port records

The following records close the proposed own-domain boundary; they are not new commands demanded of another product. Every port envelope is `{contract: "swarma-router/0.1.0", interface: Ref, action: PortAction, call_id: Ref, payload: <action record>}`. A reply is `{contract, interface, action, call_id, result: <action result>}` with exact echo binding. Unsupported field/variant/version is invalid before effects. Calls use the trusted ExecutionContext out of band, never accept a JSON-supplied authority. Qualification independently binds the exact interface/action version, actual owner and counterpart implementation. Losing echo/correlation is unknown, not a refusal with no effect.

`ReadRequest` is `{project: Ref, subjects: Ref[], expected: RevisionRef[], at: Time}`; arrays are unique and sorted. Source replies are `{project: Ref, subjects: Ref[], result: SourceResult<T>}` with exact project/subject echo, including failures. Present revision.object/source must match the source's admitted subject mapping. Subjects encode ONLY registered own-domain object refs, not ad hoc query expressions. Worker reads request member refs; model catalog reads exact configuration refs; observation reads request QuotaKey/configuration or host/runtime subjects through `ObservationRequest` below. A null source cannot be fabricated into an empty present value.

`ObservationRequest` is `{project: Ref, at: Time, configurations: Configuration[], quota_keys: QuotaKey[], local_subjects: [{host: Ref, runtime_scope: Ref, models: RevisionRef[]}], expected: RevisionRef[]}`. Configurations and keys are unique/canonical-sorted, models unique. Vendor/local replies are `{project: Ref, request_digest: Digest, result: SourceResult<VendorLimits|LocalResources>}` with the concrete value type fixed by interface; no mixed type. Missing requested observations remain unknown with coverage visible. Host consumption may be translated into VendorLimits only under its supported semantics and qualified derivation; do not open a duplicate telemetry feed when an admitted matching source suffices. Configuration is selected statically in the router config as for other optional interfaces.

### Policy projection acquisition before effect admission

`policy.read_projection` on the existing `policy/0.1` interface acquires the fresh resolved Policy value needed to assemble Snapshot.policy. Its exact capability is `swarma-router/0.1.0/policy.read_projection`. This is a source observation/preparation action, separate from `policy.evaluate` and every claim/effect. It requires no existing Snapshot, prior recommendation, DecisionStore record, cache or Policy value. A config Policy RevisionRef identifies what to read; it is not the resolved value or permission to execute.

`PolicyProjectionRequest` is `{project: Ref, task: RevisionRef, card: RevisionRef, action: route|apply, current: Origin, destination: Configuration, expected_policy: RevisionRef, caller: Ref, caller_chain: RevisionRef, attenuation: RevisionRef, at: Time}`. expected_policy equals the explicitly selected router configuration's policy pin. The caller/chain/attenuation fields must equal the trusted out-of-band ExecutionContext, project must equal its project, and at is the fresh trusted read clock. Client JSON cannot supply another caller or widen read access. Source-owner read authorization is checked without requiring the yet-unread Snapshot.policy or effect Admission. If read access cannot be established, return unknown with authority_unknown/authority_denied and no private projection, not invented absence or granted effect authority.

`PolicyProjectionReply` is `{project: Ref, task: RevisionRef, action: route|apply, caller: Ref, request_digest: Digest, result: SourceResult<Policy>}`. These echoes and SHA-256 of the canonical complete PolicyProjectionRequest bind card/current/destination/expected revision/chain/attenuation/time as well as explicit project/task/action/caller. A present result has the exact resolved Policy record defined in the Snapshot projection table, not Admission. Its revision must equal expected_policy and its observed_at<=request.at<fresh_until, observed_at<fresh_until. Its source/authority/evidence must support this project/task/action/caller view and the requested exact origin/destination. Referenced qualifications retain their full keys and are semantically validated, including current task/origin/configuration/role/difficulty matches and duplicate-key rejection. A response cannot use another task's evidence or a broader caller view to satisfy a missing assessment. Policy values may contain valid distinct keys as previously specified; only authorized matching assessments can clear the requested path.

The result union is exactly SourceResult<Policy>: present, authoritative absent, unknown, unconfigured or invalid, with the same closed fields and freshness semantics. A different revision, project/task/action/caller or request digest is rejected as stale/mismatched policy evidence before admission; a source read failure is unknown, not absent. Domain reason mapping is fixed: authoritative absence -> source_absent; unknown read -> source_unknown with the preserved authority/source reason; stale freshness -> source_stale; wrong project/task/action/caller/request digest or return type -> source_invalid. Expected-policy revision drift -> stale_decision for Apply and source_stale for Route. Unconfigured adapter -> unconfigured; configured adapter lacking this action -> capability_unavailable. A Policy with conflicting semantic keys is source_invalid/evidence_insufficient, subject=qualification_key_conflict, and cannot support effects. Unsupported policy.read_projection is capability_unavailable; returning Admission from this action or Policy from policy.evaluate is source_invalid. Boundaries retain sanitized counterpart reasons and never broaden access. Actual source-owner capability/translation remains to be qualified; declaring this own-domain action does not assert an existing external endpoint.

Route assembly is explicit: validate the trusted request; read fresh Task/Card, resolve its member/worker/current Origin and exact card destination, collect other required source facts, then call policy.read_projection with those refs/config pin/caller/action=route and fresh time. Set Snapshot.policy to the validated reply.result unchanged; do not insert wrapper fields into SourceResult. Retain the concrete request/reply pair as the policy_projection field of AdmissionRequest, so evaluation needs no undeclared cache or history. An unsupported/absent/stale/unknown/mismatched/invalid required policy refuses or reports insufficient evidence before any claim/gate/stop/launch/delivery; an already reserved no-effect operation keeps its correlation and truthful refused/unknown receipt as appropriate. Positive source acquisition itself creates no reservation. Assemble/validate the complete Snapshot/digest and frozen eligibility/semantic-key/timing/observation facts, call the existing policy.evaluate with AdmissionRequest, then reserve/acquire and execute under all original owner checks. Running still uses one exact-generation Broker delivery and zero Launcher calls; stopped still uses positive absence, exact card launch once, verified liveness then Broker. Missing Launcher cannot break the running positive trace.

Apply similarly obtains/revalidates the current pinned Policy projection for action=apply and the exact recorded/current scope, assembles the fresh Snapshot and compares expected source revisions before policy.evaluate, claims or damage. Every subsequent required policy refresh uses this declared acquisition path and current read authority; successful earlier reads do not replace fresh effect admission or actual claim/boundary verification. Changed authority/hold/source policy still blocks the next effect and preserves true partial state. Recommend remains pure and consumes its explicitly supplied frozen Snapshot; it does not call this or any other source port during selection/replay.

The source.read inventory remains exclusive as written. policy.evaluate now explicitly includes the typed request/reply pair in AdmissionRequest and still returns SourceResult<Admission>; its input/output cannot be replaced by a policy read. policy.read_projection has its own envelope/action/request/reply above and is declared in the closed action table; adapters cannot satisfy it with an undocumented cache, direct import of counterpart internals or a permissive unknown-field extension. Static policy adapter selection and qualification must declare both read_projection and evaluate capabilities for live Route/Apply. Only read access is exercised here; a fresh valid read followed by an effect-admission refusal produces zero claim/lifecycle/delivery effects.


`AdmissionRequest` is `{project: Ref, task: RevisionRef, card: RevisionRef, action: route|apply, current: Origin, destination: Configuration, slot: Ref, slot_owner: Ref, assignment_mode: existing|create, selection_input_digest: Digest|null, snapshot_digest: Digest, snapshot: Snapshot, policy_projection: {request: PolicyProjectionRequest, reply: PolicyProjectionReply}, requested_at: Time}`. `Admission` is `{owner: Ref, revision: RevisionRef, request_digest: Digest, caller_chain: RevisionRef, attenuation: RevisionRef, authority: RevisionRef, task: RevisionRef, card: RevisionRef, destination: Configuration, slot: Ref, slot_owner: Ref, assignment_mode: existing|create, observed_at: Time, valid_until: Time, allowed: boolean, timing: TimingAssessment|null, plan: TimingPlan|null, quota_requirements: QuotaRequirement[], resource_requirements: ResourceRequirement[], evidence: RevisionRef[], reasons: Reason[]}`. AdmissionRequest.policy_projection.request must match the request project/task/card/action/current/destination, configured policy pin and trusted caller/chain/attenuation; its at<=requested_at and its reply must pass the exact request digest/echo/source/freshness checks above at requested_at. Canonical reply.result must equal Snapshot.policy, with independently verified source provenance; an arbitrary JSON echo is not a trusted read. Effect admission independently revalidates actual current owner policy/evidence and cannot trust a caller-forged projection merely because digests match. Admission.plan must equal the deterministic jointly feasible-now plan computed from the supplied snapshot/timing at requested_at, with its valid_until no later than plan.valid_until; a false/unknown/invalid frozen eligibility or semantic-key check cannot yield allowed=true. PolicySource returns SourceResult<Admission>; denied may have timing=null and is present allowed=false with authority_denied/owner reason, not absent. permitted=true is not a field; assignment_mode=existing requires Task.assignee=destination.member and non-null exact Task.assignment; create requires unassigned task/null assignment and explicit current task-owner policy right `swarma-router/0.1.0/assignment.create` in snapshot.policy.allowed_actions (a policy right exercised atomically by claim.acquire, not a separate executable PortAction), atomically exercised by that owner. Reassigning another member is unsupported in Route. allowed=true requires exact assignment_mode, non-null supported timing and its jointly feasible current plan, snapshot_digest matching the supplied complete snapshot, exact request_digest, scope/config/slot equality, matching trusted chain and current valid evidence. Unknown/missing/false never progresses an effect. The actual boundary owner must validate the full current source revisions/temporal/quota/resource/policy predicates again; no opaque reference is used as the pure selector's substitute for resolved facts.

`ClaimSubject` is `{owner: Ref, project: Ref, task: RevisionRef, assignment: RevisionRef|null, member: Ref, card: RevisionRef, configuration: Configuration, slot: Ref, expected_session: SessionRef|null, stop_evidence: RevisionRef|null}`. Route-running names its exact expected generation; Route-stopped names null session and positive absence. Apply same-member names predecessor and exact destination configuration in the same slot; after stop a successor is bound only by the owner's transition result. `ClaimGrant` is `{owner: Ref, id: Ref, fencing_revision: Ref, operation_id: Ref, subject: ClaimSubject, mode: assignment|replacement, state: held|transferred|released|unknown, successor: SessionRef|null, custodian: Ref, observed_at: Time, valid_until: Time|null, evidence: RevisionRef[]}`. `ClaimBundle` is `{operation_id: Ref, grants: ClaimGrant[]}` with encoded size <=8192 bytes and at most two grants, representing all actual task-assignment and execution-slot owners; a combined owner may return one grant only if its admitted contract atomically covers both. Expected assignment equals the frozen Task.assignment; null is permitted only where Admission explicitly covers the actual task owner atomically creating the assignment for this member. In that branch confirmed ClaimGrant.subject.assignment is a non-null owner-issued revision and the only permitted change to the requested ClaimSubject; all other subject fields match exactly. An existing assignment must match its exact RevisionRef. Absent assignment authority cannot be guessed. Fencing refs are owner verification handles, not transferable credentials or router-minted permission. Claim expiry is proved only by the owner; a local timeout never proves release.

`EffectBinding` is `{operation_id: Ref, project: Ref, task: RevisionRef, card: RevisionRef, destination: Configuration, slot: Ref, slot_owner: Ref, predecessor: SessionRef|null, successor: SessionRef|null, admission: RevisionRef, timing_plan: TimingPlan, claims: ClaimBundle, expected_revisions: RevisionRef[], caller_chain: RevisionRef, attenuation: RevisionRef}`. All start payloads require not_before<not_after, both derived from this exact plan/window and remaining deadline bound; they are not caller overrides. Plan.valid_until/Decision.valid_until bound initial admission of a new operation or Apply attempt, not a later event clock inside an already admitted operation. Every subsequent effect still requires fresh owner authority, hold/claim/source checks and a feasible remaining-phase window/finish plan; an expired decision cannot start a new operation or bypass a failed current check. Same-operation Status/reconciliation remains available under current read authority, and historical proofs retain their actual event times. The store persists this exact binding before the first effectful call and each updated successor binding before later calls. `OwnerStamp` is `{owner: Ref, operation_id: Ref, binding_digest: Digest, owner_revision: Ref, observed_at: Time, evidence: RevisionRef[]}`. Receipt.operation_id, stamp.operation_id, claims.operation_id and binding.operation_id must match. Stamp.owner must equal the admitted action owner; binding_digest covers the entire current EffectBinding. Session/task/configuration/claim/generation equality is structural, never matching only a name/PID. New successor stamp is accepted only from the exact correlated launch operation and then becomes expected in the persisted binding.

For all effect actions, `EffectResult<T>` is exactly one of:

- `{status: "confirmed", stamp: OwnerStamp, value: T}`; only the action's typed value can advance its phase.
- `{status: "no_effect", owner: Ref, operation_id: Ref, binding_digest: Digest, verdict: refused|unsupported|conflict, reason: Reason}`; the owner positively attests this call made no effect. Prior effects/grants are retained in the operation's receipt, so this tag alone cannot turn a partial operation into refused.
- `{status: "unknown", owner: Ref, operation_id: Ref, binding_digest: Digest, correlation: Ref|null, possible_effect: boolean, last_phase: Phase, gate: not_applicable|open|closed|unknown, reason: Reason}`; unknown never progresses an unproved phase. possible_effect=false still does not fabricate a success or a released claim. A lost reply is normalized to unknown with possible_effect=true and known original correlation; missing correlation leads to reconciliation_unavailable. External refusals preserve sanitized native code.

Claim acquisition precedes a full EffectBinding because it creates claims: `ClaimRequest` is `{operation_id: Ref, project: Ref, admission: RevisionRef, subjects: ClaimSubject[], mode: assignment|replacement, caller_chain: RevisionRef, attenuation: RevisionRef}`. Its request digest is the binding_digest for Claim results. Acquire returns EffectResult<ClaimBundle>; partial multi-owner acquisition is unknown/partial with grants retained, never a false atomic bundle. Validate/Retain/Release requests are `{operation_id: Ref, bundle: ClaimBundle, expected_fencing: Ref[]}`. Transfer adds `new_custodian: Ref, destination: SessionRef`; no other fields. These actions return EffectResult<ClaimBundle>, with the same canonical request digest binding. Claim.Status instead takes `{operation_id: Ref, project: Ref, acquire_request_digest: Digest, correlation: Ref}` so a lost Acquire reply can recover the original grant without already knowing its bundle. It returns the same EffectResult<ClaimBundle>, bound to this lookup request and validated against the original durable ClaimRequest; it never performs Acquire again. Claim.Status is observational; unknown custody remains unknown. Each grant must be independently verified with its actual owner and original subject/fence; an adapter wrapper stamp cannot substitute for those owners. Each effect owner also validates the held current bundle at the real effect boundary.

`OwnerOperationState` is `{phase: Phase, state: pending|succeeded|refused|failed|partial|unknown, effect: none|present|unknown, predecessor: SessionRef|null, successor: SessionRef|null, gate: not_applicable|open|closed|unknown, claim_bundle: ClaimBundle, stop_evidence: RevisionRef|null, handover: RevisionRef|null, restore: RestoreEvidence|null, input: InputEvidence|null, ready: ReadyEvidence|null, resume: ResumeEvidence|null, delivery: DeliveryRef|null, reconcile_required: boolean}`. Nulls mean unestablished facts; only non-null correctly bound confirmed evidence can advance the matching phase. Phase/responsiveness alone cannot imply readiness. Owner result and router Receipt must agree on retained effects, generation and gate; an inconsistent/conflicting reply is invalid and operation unknown pending reconciliation.

Claim custody is explicit. Acquire/Validate creates no task completion or resource metrics authority. Through queue acceptance/Apply complete, retain held grants or transfer only through owner-confirmed claim.transfer to the exact admitted execution/queue custodian that keeps assignment/delivery fencing; success may retain grants and report that custody, not automatically release. After a no-effect refusal, release held grants only through owner-confirmed release if no live assignment/inflight/uncertain effect depends on them. Partial launch, queue acceptance, restore failure, lost acknowledgements or unknown status retain ownership and reconciliation duty; do not force release or treat a local lease as reusable capacity. A release attempt with unknown outcome retains unknown claim state and forbids replacement allocation pending owner Status. A transferred claim retains its immutable original operation correlation. Task completion/release belongs to the actual owner, not this router's successful delivery. A claim alone is not reservation of CPU/RAM/provider quota unless the exact independent owner contract explicitly includes that admission.

Storage ports are also closed. `decision.put` takes `{scope: {caller: Ref, project: Ref}, decision: Decision, input: SelectionInput}` and returns `{status: stored, id: Digest}` or `{status: unavailable, reason: Reason}`; it validates all digests/aggregate budgets atomically before stored. `decision.get` takes `{scope, id: Digest}` and returns `{status: found, decision: Decision, input: SelectionInput}` or `{status: absent|unavailable, reason: Reason}`. Found must hash to the requested id and original complete input; unauthorized is unavailable/authority_denied, not leaked existence. Storage location/request correlation is excluded from pure identity.

`OperationRecord` is `{key: OperationKey, request: <exact Route or Apply request>, receipt: Receipt, binding: EffectBinding|null, correlations: [{owner: Ref, action: PortAction, correlation: Ref, request_digest: Digest}], proofs: [{owner: Ref, action: PortAction, stamp: OwnerStamp, value_digest: Digest, artifact: RevisionRef}]}`. These bounded arrays are unique/canonical ordered; proof artifacts must be durably retained in the admitted owner/store, not unresolvable hashes. Binding and owner correlation are written before each effect call; a failure prevents that next call, while previous possible effects remain reconciled. An unknown reply with no newly received proof does not erase prior correlation/binding. Request type is fixed by receipt.operation_kind; semantic request_digest excludes only request_id and includes every other request field.

`OperationKey` is `{caller: Ref, project: Ref, kind: route|apply, key: Ref}`. `operation.reserve` takes `{key: OperationKey, request_digest: Digest, initial: OperationRecord}`; initial.receipt is validated/none/no claim with durable owner operation correlation allocated before any external call. It returns `{status: reserved|existing, record: OperationRecord}` or `{status: conflict|unavailable, reason: Reason}`. Identical key/payload existing returns exactly that operation; conflict cannot alter it. `operation.cas` takes `{key: OperationKey, operation_id: Ref, expected_revision: integer, replacement: OperationRecord}` and returns `{status: updated|conflict, record: OperationRecord}` or `{status: unavailable, reason: Reason}`. Updated receipt.revision must be expected+1; operation/key/request_digest never change. `operation.get` takes `{key: OperationKey|null, operation_id: Ref|null, caller: Ref, project: Ref}` with exactly one selector non-null, returns `{status: found, record: OperationRecord}` or `{status: absent|unavailable, reason: Reason}`. Unknown read never licenses re-reservation after possible effects. Capabilities for these actions follow the same versioned name rule. Store responses are not lifecycle proof; owner evidence is required separately.


## Deterministic identity and replay subset

The digest-bearing own-domain JSON is canonicalized by this proposed version: recursively sort object keys by the unsigned byte order of their valid UTF-8 encoding; serialize arrays in their declared order; use integer decimal notation with no leading zeros or negative zero; use true/false/null literals; emit valid non-control Unicode in UTF-8 without normalization; escape double quote/backslash and controls U+0000–U+001F using lowercase `\u00xx`; omit all insignificant whitespace. Reject invalid representation before canonicalization. Semantically equal timestamp values must already use the canonical Time form. The arrays `members`, `workers`, `entries` are sorted respectively by member/member/id Ref; Usage.events uses its declared scope/time/id order; vendor observations by canonical QuotaKey, machine observations by host, inventories by host/runtime_scope, models by canonical model RevisionRef, requirement arrays by canonical whole record, claims by owner/canonical subject/id, correlations/proofs by owner/action/correlation or artifact; admitted configurations by canonical whole-record bytes and qualifications by canonical QualificationKey (unique semantic keys, not merely unique whole records); Ref sets (roles, project_scope, active_assignments when non-null, allowed_actions, capabilities) lexicographically by Ref; RevisionRef evidence/constraints arrays by canonical whole-record bytes. Duplicates are invalid. Preference order, alternatives rank, interval order and reason order are meaningful and preserved; the selector emits interval order by start/end/priority and reasons by code/source/subject then canonical whole-record bytes.

snapshot_digest is SHA-256 of the canonical Snapshot. selection_input_digest is SHA-256 of canonical SelectionInput, preserving explicit current_member/target_member nulls. Decision.id is SHA-256 of canonical `{contract, selector_version, input: SelectionInput, result_without_id}`, where result_without_id is the complete Decision record with only id removed. request_id, storage location, UI rendering and transport retry metadata are excluded. Structured reasons including their messages are included; free-form message generation must therefore be deterministic or frozen. A changed dependency/estimator/selector/policy/time yields a new digest. A canonical key tombstone cannot be reassigned to another payload.

Replay reads the complete stored SelectionInput and frozen estimator output, verifies its digest and runs the named selector with exactly that input and compares its structured result. A newer selector may produce a new result but must not pretend it is the old decision. Replay proves only deterministic selection from recorded inputs, not correctness/calibration of the inputs or repeatable model execution. Storage and canonicalization fixtures must include Unicode keys, explicit nulls, duplicate/invalid fields, meaningful list order and changed policy versions. This is a proposed subset to be qualified before release, not a claim of compatibility with another JSON canonicalization standard.
